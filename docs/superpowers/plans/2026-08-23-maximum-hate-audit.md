**Teardown**

This repository is not “fixed.” It is still a pile of cargo-culted systems code with a nicer haircut. The recurring pattern is simple: global mutable state, detached background work, weak or nonexistent trust boundaries, and failure handling that amounts to “shrug and hope DNS solves itself.”

**Findings**

1. **The DNS server is single-threaded in the dumbest possible place, so one slow lookup stalls the whole resolver.**  
   The main UDP loop does everything inline: packet unpacking, process attribution, exclusion checks, upstream forwarding, stats updates, and ring-buffer writes. There is no worker pool, no per-request goroutine, no bounded concurrency, nothing. `GetProcessInfoForPort` can do a full system PID/FD sweep under a global lock before the request is even classified, and `RaceForward` then waits up to 500 ms. That means one expensive query can head-of-line block every other client behind it. Calling this a DNS daemon is generous; it is a serialized control path wearing a UDP hat.

2. **The “race” forwarder is UDP vandalism: it sprays every query to every upstream and trusts the first blob that comes back.**  
   `RaceForward` fans out one goroutine per upstream for every request, writes the same packet to all of them, then accepts the first response bytes without validating that the answer actually matches the original question, source, or even the same DNS ID. That is not resilience; that is cache-poisoning bait. It gets worse in `forwardQuery`: the returned packet is unpacked and cached under the original `domain`, but the cached type comes from the response’s first question. So a malicious or merely broken upstream can hand back a mismatched response and this code will happily store the lie. This is amateur-hour networking.

3. **Failure handling in the forwarding path is “drop the packet and say nothing,” which is exactly how you create ghost outages.**  
   If upstream forwarding fails, `forwardQuery` returns without sending any response at all. No `SERVFAIL`, no timeout reply, no retry strategy, no telemetry beyond silent absence. The same style shows up everywhere: UDP write errors are discarded, DNS pack/unpack failures are discarded, malformed client packets are discarded. This codebase loves invisible failure because invisible failure lets the author pretend the system is fine. Production users call that “DNS randomly hangs.”

4. **The IPC surface is still an unauthenticated local control plane with a world-writable socket.**  
   The daemon removes whatever is at `SocketPath`, binds a Unix socket, then chmods it to `0666`. `/stats` leaks query telemetry to any local process. `/queries` dumps activity history to any local process. `/pause` flips global filtering state for any local process that can write JSON. There is no peer credential validation, no authorization, no method restriction beyond accidental JSON decode behavior, and no attempt to bind policy to the owning user. Moving this from `/tmp` to `/var/run` did not make it secure; it just changed the location of the bad idea.

5. **Swift side-effects are wired through `didSet` like a beginner discovered property observers and stopped thinking.**  
   `AppViewModel.isDnsActive` mutates system DNS as a side effect in `didSet`. That means a UI state flip is also a privileged network configuration change. Then `pauseProtection` and `enableProtection` mutate that flag after the IPC call, which triggers detached DNS-helper work, which shells out to `networksetup` on background queues. This is not MVVM. This is a Boolean landmine hooked to system configuration. Worse, the view model has no source of truth from the daemon; it just assumes the local shell-out and the daemon pause state remain aligned. That is how you get the menu saying “active” while the actual network state is something else entirely.

6. **I did not find a textbook Combine retain cycle. I found something more primitive: detached tasks that outlive ownership and cannot be coordinated.**  
   The Combine sinks at least use `[weak self]`, so congratulations on clearing the absolute lowest bar. The real memory/lifetime rot is the unstructured task abuse: `IPCClient.fetchStats`, `fetchQueries`, `sendPause`, `AppViewModel.handleDnsStateChange`, and `ExclusionModel.saveExclusions` all launch detached work with no ownership model and almost no cancellation. If the view disappears, timers can be cancelled, but already-launched detached tasks keep running. If the model deallocates, they keep doing work anyway. This is not a retain cycle problem; it is a lifecycle-control problem caused by people treating `Task.detached` as holy water.

7. **The Swift transport is a fake HTTP client that does not understand HTTP and barely understands sockets.**  
   `UnixSocketTransport.sendRequest` does a single `send`, assumes the full request was written, never checks for partial writes, never checks HTTP status, never validates headers, and returns the body even if the server returned an error. That means the UI can decode garbage as success or silently fail into stale state. This is the same fraud pattern as the Go side: move bytes, ignore protocol semantics, and hope the happy path covers the embarrassment.

8. **Polling and decoding errors are intentionally swallowed, so the UI is designed to lie quietly.**  
   `IPCClient` catches and ignores polling failures. Query decoding uses `try?` per line, so malformed records are dropped one by one without surfacing corruption. `ExclusionModel` logs to stdout and keeps going. `runProcess` returns error text as a normal string, and callers treat it as if it were valid command output. This is a codebase built by someone terrified of explicit error states because explicit error states would force them to admit the control flow is bad.

9. **Background goroutines and timers are started casually and almost never owned or stopped correctly.**  
   `StartGravitySync` launches a 24-hour ticker and never exposes a shutdown path. `process_monitor.init` starts a permanent janitor goroutine with its own ticker and no stop path. `handleSignals` registers for signals and calls `os.Exit(0)` from a goroutine instead of coordinating shutdown. The watcher code in exclusions/userlists sprays `time.AfterFunc` timers around with no lifecycle discipline. None of this is catastrophic alone; together it screams “no one designed process lifetime, they just kept appending goroutines until the tests stopped yelling.”

10. **The tests are mostly theater and miss the exact places where the implementation is fraudulent.**  
   The forwarder test uses `net.Pipe`, which is not UDP, not DNS, and not reality. The IPC test only checks that `/stats` returns `200`, not that authz exists, methods are constrained, or pause state is safe. The Swift tests validate that flags flip, not that system DNS changes are coordinated, cancelled, or reversible. The suite does not meaningfully attack the code’s trust boundaries or concurrency model because that would require admitting those boundaries do not exist.

**Bottom Line**

The deepest rot is architectural, not cosmetic:

- The DNS path is serialized and over-coupled to expensive process inspection.
- The forwarding layer does not enforce response authenticity before caching or returning data.
- The IPC plane is unauthenticated local control.
- The Swift app uses UI state as a trigger for privileged system mutation.
- The entire failure strategy is “swallow errors until the user gets confused.”

I also ran `go test ./src/dnsd/...`; it failed in this sandbox because `httptest` could not bind a port, so I could not use runtime results to validate or dismiss the source findings. That limitation does not rescue the code. The main problems are visible directly in the implementation.
